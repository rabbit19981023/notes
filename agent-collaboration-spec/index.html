長任務裡，背景工作每完成一次，就叫醒主線回一段。每一段單看都合理，疊起來就出現五個症狀，分成兩類。

讀者端：你讀得很累

  • 重複的資訊
  • 重點被埋在某個角落，要全部讀完才敢確定沒漏
  • 前後矛盾

Context 端：agent 變笨、變貴

  • 雜訊引發幻覺
  • 浪費 context 與 token

兩類都要從根本解決。只讓畫面安靜、context 照樣被佔的做法不算數。

十一條規則

P1 檔案當記憶

計畫、進度、決策、結果、證據都寫進檔案，存在會留下來的地方：暫存區和雲端容器都會被清掉，值得保留的要 commit 或推上去。對話的自動摘要不算記憶，因為看不出留下了什麼。沒寫進檔案的事，對接手的 agent 等於不存在。

P2 對話用完就丟

任何角色只靠檔案就能接手。預設每個階段新開乾淨的 context，只帶上一階段的產出進場，不帶對話紀錄。同一範圍的延續或修正可以續用同一個 agent；驗證一律新開，主線自己做的小修改除外。

P3 只傳參照，不傳全文

角色之間不靠長訊息傳話。下層把產出寫進檔案層，只回固定幾段：結論、做了哪些決定、證據、風險，加上路徑。上層拿路徑去讀整理過的精華報告，不讀過程。往上只交一次最終報告，不傳進度，也不透過回報提問。

P4 寫入單線

同一批檔案，同一時間只有一個寫入者。每份文件只有一個擁有者，擁有者就是負責那一層的角色。其他角色貢獻判斷，不動手改。

P5 狀態和日誌分開寫

兩者都要。狀態回答「現在是什麼情況」，會被改寫，給你讀。日誌回答「發生過什麼」，只追加，給接手的 agent 和追查時用；日誌就是 git 歷史，加上各計畫的 Surprises & Discoveries。兩種寫法不混用。

P6 用驗證取代閱讀

你不讀過程，也不逐行讀產出，只檢查驗證產物：影片、截圖、圖表、測試與形式化驗證的輸出。驗證分兩層：做事的人先自驗，再由沒看過過程的驗證者驗收，主線只收一份驗收報告。主線自己做的小修改除外，由主線自己驗。

P7 主線保持短

長任務不放在主線跑。主線派工一律派子主線，自己只寫派工和決策，讀子主線交回的精華。例外：範圍有限的小任務（幾次讀檔、一次搜尋、一個小修改、一次檢查）主線自己做，做完也由主線自己驗證，因為派工的成本和每次交接的損失都比好處大。小修改只限沒有子主線擁有的檔案。

P8 計畫由做事的人更新，狀態由程式組出

每個任務的 ExecPlan 是活文件，由負責的子主線隨進度、新發現和定案的設計決策持續修訂。全局狀態不用 LLM 重寫，由程式從各計畫檔組出來。

P9 主線只在三種時機對你開口

Agent 的結果不轉述給你，只寫進檔案。主線只在需要你決策、到了檢查點、你主動問的時候開口。工具內建的行為若是結果一到就摘要給使用者，以這條為準。

P10 主線先弄懂才派工

主線要完整理解這件事，並先把派工的內容想清楚、寫清楚，才能派工。寫不出清楚的派工單，就代表還沒懂到可以交出去。每一次資訊傳遞都有損失，派工單不清楚只會放大損失。沒懂就派，下層會做白工、回一堆雜訊，甚至整件事做錯，主線的 context 也跟著毀掉。

P11 理解的人寫，乾淨的人查

產出由最懂的人寫：做事的 agent 寫自己的報告，主線寫給你的回覆。查核交給新開、沒看過過程的角色，它只核對每一點是否指得回證據，回報不符之處，不改寫。沒看過過程的角色不重寫別人的成果，那只是多一次轉述。

主線派子主線，子主線帶 worker

  • 主線派工一律派子主線，依任務類型派一到多個。
  • 子主線是這一類任務的 leader：派 worker、綜合各 worker 的結果、交出最終的精華報告。只有一個 worker 時，子主線自己就是那個 worker。
  • 子主線把較小的任務派給平行的專門 worker，前提是它們不改同一批檔案。
  • Worker 的報告固定分成結論、決定、證據、風險幾段。程式把同一個子主線底下的報告併成一份，不改寫任何內容；綜合並交出最終答案的是子主線。
  • Worker 多到子主線讀不完時，主線改派更多子主線，不多加一層。
  • 主線拿參照去讀子主線的精華報告，不讀 worker 的過程。
  • 例外：範圍有限的小任務，主線自己做，不派子主線；小修改只限沒有子主線擁有的檔案。
  • 層數上限兩層：主線 → 子主線 → worker。Worker 不再往下派。
  • 要帶 worker 的子主線用新開的 agent。繼承上層整段 context 的分身（fork）只做事，不再往下派。

派工的規矩，每一層都適用

  • 派工單要自足：目標和原因、已排除什麼、範圍（包括哪些是別人負責的）、完成的樣子、只研究還是可以修改。查詢給確切指令，調查給問題，不給步驟。
  • 理解不外包：讀完下層的精華，寫出具體的下一步，不寫「根據你的發現去做」。
  • 派出去就交給它：不重做、不重推它的發現，執行中也不去看它的過程。
  • 小任務自己做，少開 agent，不為一件小事開好幾個平行。
  • 續用或新開：修正失敗、延伸剛做的事，續用同一個；驗證別人的成果、換方法重來、不相關的事，新開。

主線自己讀，還是派出去讀

判斷標準不是檔案多不多，也不是任務大小，而是讀完的內容之後還用不用得到。

主線自己讀派出去讀
要靠這些內容做決定、寫派工單（P10 要求主線必須懂）要在大量內容裡找東西，事先不知道在哪
之後還會一再用到讀完只需要結論或位置
範圍已知，就是那幾個檔會讀到大量用不到的東西：log、搜尋結果、整個目錄

兩者合用最常見：先派出去定位，回報位置和摘錄，主線再自己讀關鍵段落。

角色是職責，不是固定的 agent 數量。一個職責可以由多個 agent 分擔，但同一個 agent 不同時負責「做」和「驗」。

狀態永遠只留現況，日誌只追加、不回頭改。每份文件只有一個擁有者。

任務計畫用 ExecPlan

每個任務一份 ExecPlan，由負責的子主線隨進度修訂。它有六段：

  • Progress：勾選清單，永遠反映現況。每個停下來的點，都記下已完成和還剩下的部分。
  • 需要你決策：卡住、等你決定的事。
  • 需要你注意：沒有卡住，但你應該知道的風險或異常。
  • Surprises & Discoveries：意料之外的發現和走過的死路，接手的人不必重走。
  • Decision Log：這個任務內的決定直接寫在這裡，一兩行就好。會影響其他任務、或難以回頭的決定寫成 ADR，這裡只放連結。
  • Outcomes & Retrospective：結束時寫：做到了什麼、和原目標差多少、學到什麼。

你常問的從哪裡來

總整理由程式組出來，主線再在上面寫一段短回覆，見 /reply 一節。

日誌就是 git 歷史

每個有意義的步驟一個 commit，commit 訊息用 Conventional Commits 的寫法。只有要對外發佈時，才另外維護 Keep a Changelog 格式的 CHANGELOG。

大量平行任務時，避免互相踩到

原則：能用「單一擁有者」避開的併發，就不用鎖；剩下非共用不可的，才加鎖或交給單一角色依序做。

  • 每個任務一份 ExecPlan，只有負責的子主線能寫。計畫之間不共用檔案，就沒有併發寫入。
  • Worker 不寫計畫，只交報告給子主線。
  • 衍生檔（全局狀態、總整理、ADR 的四份索引）由程式產生，不手改。產生時先寫到暫存檔，再整個換上去；重跑結果一樣，同時跑也不會寫壞。
  • 平行分支上不提交衍生檔，合併後由整合者重產一次，所以不會有合併衝突。
  • ADR 用時間戳命名，平行任務各自建立也不會撞號，不需要配號。
  • 必須互斥的動作，例如合併到主分支，一次只讓一個 agent 做：用鎖，或固定交給單一角色。
  • 會改到同一批檔案的工作，沿用「預設不拆」的規則。

決策用 ADR 記錄

  • 只有會影響其他任務、或難以回頭的決定寫成 ADR。任務內的決定寫在該任務 ExecPlan 的 Decision Log。
  • 一個決策一份檔案，放在 decisions/，檔名是時間戳加簡短英文標題，例如 20261123-1955-use-worktree-isolation.md。平行任務各自建立也不會撞號，不需要配號。
  • 每份 ADR 有四種狀態：提議中、暫時生效中、生效中、已被取代。被取代時，連到取代它的那份 ADR。
  • 提議中：還沒生效，等你決定。符合「重大」判準的決定（例如難以回頭）一律先寫成提議中，你確認後才生效、才開始做。
  • 暫時生效中：先照這個決定往下做，到下一個檢查點交給你確認。用在會影響其他任務、但可以回頭的決定。你確認後改為生效中；你否決的話，就寫一份新的 ADR 取代它。
  • ADR 寫好之後不再修改，只有狀態可以變。決策改了，就寫一份新的 ADR 取代舊的。
  • 四份索引由程式從各 ADR 的狀態產生：decisions/proposed.md 列提議中的，decisions/provisional.md 列暫時生效中的，decisions/active.md 列生效中的，decisions/superseded.md 列已被取代的。Agent 平時讀 active.md 和 provisional.md，這兩份是正在生效的決定。
  • ADR 只記決策。進度這類流水帳不寫成 ADR。

暫存和保留分開

.scratch/ 放進行中、可丟棄的檔案，例如中間產物、草稿、原始輸出，不進版控。值得保留的，移到會 commit 的地方。

/reply：程式組出的狀態，加上主線寫的回覆

  • 狀態由程式組出，不經 LLM 轉述。
  • 回覆由主線寫。主線讀過每個子主線的精華報告，是最懂整件事的角色。
  • 到檢查點之前，主線的回覆先交給查核者核對；查核者只回報指不回證據或互相矛盾的地方，由主線修正。

每件工作落在四組之一

  • 需要你決策卡住了，你不決定就不會往下走；不可逆或對外的動作（推送、發佈、刪除）也算。主動通知你，不排隊等你回來。
  • 需要你注意沒有卡住，但出現風險或異常，你應該知道。
  • 還剩下正在做，或排著還沒做。
  • 已完成做完，而且附上證據。沒有證據不算完成。

回覆與回報的要求

  • 先結論，再細節。
  • 每一點都指得回證據。
  • 同一件事只出現一次，前後不矛盾。
  • 如實：失敗附上輸出、跳過的要說、驗證過就直說不打折；還沒回來的結果不能先寫。
  • 給建議，不給選項清單；不重講已確立的事、不重議你定過的決定、不提不會做的選項。
  • 結案寫三件事：做了什麼、成果在哪、下一步要跑的指令。
  • 列出做了哪些決定，包括沒被要求、自己判斷的事。

驗證分兩層，宣告完成前一定有人看過實際變更

  • 第一層：做事的人先自驗，再回報完成。
  • 第二層：新開一個沒看過過程的驗證者，只給它需求和程式碼。不給上層的假設或結論，因為交出去的假設通常會被確認回來。
  • 驗證要證明它能動，不是確認它存在；要測邊界和錯誤路徑；失敗要追查，不能一句「無關」帶過。
  • 宣告完成前，驗證者要看過實際的變更。驗收由驗證者做，主線不自己驗收，只收一份驗收報告。
  • 例外：主線自己做的小修改，由主線自己驗證，不另開驗證者。

會改到同一批檔案的工作，預設不拆

主線依任務類型派子主線，子主線再視需要拆給 worker，不需要你逐一派工。拆之前先問一個問題：這兩件工作會改到同一批檔案嗎？

不會

平行

各開各的 session，各寫各的檔案。

會 · 預設

依序

交給同一個寫入者，一件做完再做下一件。

會 · 例外

隔離後平行

各自在隔離的工作副本裡做（例如 git worktree），並指定單一整合者負責合併。

!

隔離擋不住隱性決定。工作副本擋得住檔案互蓋，擋不住兩邊各自對風格、邊界情況、慣例做的決定，合併時仍會衝突。所以平行寫入只當例外。

同時進行的數量不設上限。出現你檢查不過來、或品質下降的情況時，再加上限。

你只在四個時機介入

  • 檢查點研究完成後
  • 檢查點重大設計決定前
  • 檢查點發佈前：看驗證證據，也看架構層的變動
  • 任何時候出現需要你決策的事，主動通知你

前三個是固定的時間點，第四個是隨時可能發生的中斷。這四個時機之外，agent 自己往下做，不需要你盯著。

設計決定符合任一條就算重大：不可逆、會改到介面或資料結構、偏離原計畫、有兩個以上合理的選項。拿不準就問你。

你的核准要逐字送到動手的那一層

  • 核准不會自動往下傳，agent 之間傳的訊息也不算你的核准。主線要把你的原話逐字交給實際執行的 agent。
  • 核准只對那一次、那件事有效，不延續到下一個情境。
  • 讀過不可信內容（網頁、PR 文字、外部檔案）的 agent，和執行高權限動作的 agent 分開。執行者只拿核准過的那一步，不重讀那些內容。
  • 不可逆或對外的動作（推送、發佈、刪除），預設要你核准。

工具還沒補上的缺口，用繞的

以 Claude Code 為例：在單一 session 裡，背景通知會逐一觸發主線回覆。撰寫這份規格時，沒有找到能合併或延後這些通知的設定。

規格的做法是繞過它，也就是 P7：長任務交給背景 session 或 workflow，主線不會被反覆叫醒。

Claude Code 的內建規則要求 agent 結果一回來就摘要給使用者，和 P9 正好相反。實作時要把 P9 寫進專案指示（例如 CLAUDE.md），否則洪水會照舊。

分層派工需要子主線能再派 worker，也就是巢狀 subagent。Claude Code 是否允許、允許幾層，取決於版本和設定，實作前先實測。它的 fork 依內建規則不再往下派，所以要帶 worker 的子主線用新開的 agent。

!

靜音只是補丁。要求主線不回話、或把畫面上的文字換掉，畫面會安靜，context 照樣被佔。可以當過渡，不能當解法。正解是看分好組的狀態（例如 Claude Code 的 agent view），不是讀訊息流。

這份規格不決定的事

下面這些留給實作者設計：

  • 檔案的格式、欄位和目錄結構（ADR、ExecPlan 的段落、.scratch/ 除外）
  • 各角色的提示詞
  • 用哪個工具的哪個功能來開 session、隔離工作副本、發通知
  • 子主線怎麼依任務類型劃分、一次派幾個
  • 狀態怎麼從任務計畫組出來
  • 四組狀態用什麼畫面呈現

實作可以自由選擇，只要十一條規則，以及每個角色「不做什麼」那一欄都守住。
