02 · 心法

十條心法：工具會換，這些不會

從她的演講、貼文、pstack 原則裡收斂出來。後面每一節的做法，都是在落實其中幾條。

trust → throughput

信任才是產出

要問「做到什麼程度我才敢不看」，而不是「還能多開幾個 agent」。還不信任就開 100 個，只會得到垃圾 PR。

codebase = memory

程式碼庫就是 agent 的記憶

agent 照抄它看到的東西。workaround 會像雜草蔓延，所以人要當園丁：拔草、搭支架。

correction → structure

每次糾正都變成結構

與其每次在 review 裡糾正，不如改成設計、lint 或 skill；同一個錯第二次出現就升級。

right ≠ good

證據勝過說法，對的不等於好的

驗證是整條線的限制步驟，就像早餐工廠裡最慢的那顆蛋（她借《High Output Management》）。但驗證只保證做到了，不保證快、不保證省。

intent is the bottleneck

意圖才是瓶頸

模型越強，限制越落在人能不能把意圖講清楚。她從不讓 agent 替她寫文件、推文或 prompt：寫作就是思考。

code is the spec

不先規劃，用程式碼規劃

她說不相信 planning。能用實驗決定的問題，就先做原型讓結果決定；計畫做完就刪。

judgment vs. mechanics

判斷交給 LLM，機械交給 CLI

確定性的步驟寫成固定腳本，skill 只是外面一層薄包裝。現寫的腳本會漂移，同一個基準就量不出同樣的結果。

reasoning > rules

寫成推理，不寫禁令

禁令在沒寫到的情況會失效，推理能讓 agent 自己判斷。她認為模型越強，skill 會壓縮成原則或流程。

context, not control

人是主廚，不是工廠廠長

她劃掉「software factory」：工廠這個詞不談品質。量大時只能抽樣嚐；多個 agent 犯同一個捷徑，就修廚房。

verifiable

能驗證，才放手

可驗證性決定能放手多少；她說能驗證，單向門也會變成雙向門。真正難驗證的，她公開說自己沒有答案。

03 · 防線

力氣先花在最硬的那一層

每次要糾正 agent，先問最上層擋不擋得住。越往下，越容易被 agent 跳過。

規則升級成機制：一個實例

CLAUDE.md 的規則
lint-arch.sh 強制
違規輸出附修法與原則路徑

她的開源專案 noodle：CLAUDE.md 規定錯誤訊息要描述失敗狀態，lint-arch.sh 再把它強制化，違規時直接印出修法和原則檔路徑。

寫好一條檢查的五件事

本頁從她在 React Compiler 和 pstack 的做法歸納，她沒列過這張清單。

寫給 agent
錯誤訊息要列出可能情況和各自修法2025-12 她在 React 加了給 agent 讀的 lint 訊息：靜態分析判斷不了時，把三種情況與修法都列出來，讓 agent 先推理再修
先失敗
新檢查要先在當初那個真實錯誤上報錯沒看過它失敗，就不知道它擋得住
跳過要回報
可以只跳過那一處，但不准沉默跳過React Compiler 的做法：違規只跳過那個函式，但一定要出診斷
不准壞
守門工具本身永遠不能 crashlint 遇到看不懂的東西就記 log、照常運作
要修剪
沒擋到東西的規則就刪她親手刪掉自己加了一年的「沒用到的 opt-out」lint
04 · 驗證

要證據，也要驗證「驗證」本身

Code review 縮小成看證據：影片、截圖、狀態圖、證明。她說自己大部分 token 花在驗證，但書是：驗證只是近似值。

好的驗證產物要同時做到三件事

條件 1

證明是對的

跑真正的使用者路徑，讀實際的值；寫入要讀回來。

條件 2

符合原本的意圖

不只是沒有 bug，還要確認 agent 懂了你要什麼。

條件 3

比整個 PR 好審

UI 交影片或截圖，流程交狀態圖。人看證據，不看 diff。

什麼算證據

不算
能編譯、CI 綠燈、bot 核准、作者說測過了她看過 agent 一口咬定根因，翻開 tool call 才發現它根本沒讀那段程式碼
不算
「看，它打開了」的截圖同一段錄影要有觸發動作和穩定的終點狀態
有條件
eval 只能事後讀狀態不能拿來直接呼叫內部 handler 當主要證明
有條件
mock 只有放在正式邊界後面才算到不了的路徑要點名原因，改測最近的真實路徑
算
先跑 doctor，再像使用者一樣操作確認跑的不是舊 bundle；驗副作用：DOM、剪貼簿、網路 log、檔案

驗證 skill 也要先被弄壞一次

形式化驗證：從狀態圖到可重跑的證明

statechart
規則寫成 TLA+ INVARIANT
TLC 找最短反例
畫成 PM 看得懂的圖
拿真程式重播
TLA+
跨裝置通知流程model checking；規則不准為了過關放寬
Lean
自製虛擬化列表不閃爍、不抖動定理證明
Bombadil
UI 的 property-based testingAntithesis 出的函式庫，已抓到 UI bug

pstack 的 statechart 不是畫圖工具，是 TLA+ 檢查器加上讀者看得懂的圖。她說形式化方法還在實驗，不是銀彈，只是多一層。

05 · 放手

放手多少，看能不能驗證

信任要一步步建：她教 bot 的四步

在旁邊看、糾正
對話結束寫成 skill
磨到一次就對
才設 routine

她把「讓 agent 自己 merge 自己的 PR」當成目標往回推，說這是她到每月 2,000 PR 的關鍵。

建一條可信 loop 的五件事

1
先手做一次知道好的結果長什麼樣
2
給 agent 你用的工具和訊號DevTools、trace、heap snapshot，不是只給 prompt
3
每個階段都要證明自己，達不到就停失敗在越便宜的階段被擋下越好
4
讀對話紀錄，把反覆的失敗變成工具、skill 或 eval
5
loop 贏得信任後才讓它自己跑

出自她 2026-06 的長文〈Loops You Can Trust〉。

!
不要跳級。她花了約六個月才從「盯著 1 到 5 個對話」走到每月數千個 PR。信任不夠就自動化，只會更快地產出 slop，外加一大筆 token 帳單。信任曲線的五個階段見系統頁。
06 · 日常

她怎麼下指令、怎麼派工

寫進去

好 prompt 最多五件事

目標、能判過或不過的完成檢查、要看的證據、你已經知道的、真正的限制。

不寫

刻意不寫兩件事

怎麼做，以及你對原因的猜測。猜測會讓 agent 只在你指的地方找。

先重述

in your own words

先叫 agent 用自己的話重述問題，再開始動手。控制詞：「new task」「don't change any code yet」。

終點

時間不是結束條件

給一個會過或不會過的條件，不要給「做四小時」。
